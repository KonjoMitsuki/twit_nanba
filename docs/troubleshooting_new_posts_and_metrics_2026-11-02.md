# 新着投稿の取りこぼし・メトリクス取得タイムアウトの調査と修正

調査・修正日: 2026-11-02。時刻の表記は、特記がない限り日本時間です。

このセッションでは新着検知と既存投稿のメトリクス取得について、別々の原因を確認して修正しました。本書は確認した事象、原因、対策、検証結果と本番への反映状況を記録したものです。

## 1. 新着投稿を「新着なし」と判定する問題

### 事象と確認結果

対象は [投稿 `2116865529227128937`](https://x.com/nnkinnb/status/2116865529227128937) です。利用者から、11月2日8時ごろに取りこぼしに気づいたとの報告がありました。調査初期には、Notion・SQLiteともに対象投稿が未登録でした。

本番の保存済みセッションでプロフィールを開き、読み込みの順序を測定しました。

| ページ遷移開始からの経過時間 | 状態 |
| --- | --- |
| 8.80秒 | プロフィールの外枠である `main` が表示された |
| 14.22秒 | フォロワー数の取得が終わり、現行コードが投稿件数を数える時点では0件だった |
| 22.69秒 | 投稿カードが表示され、対象投稿のID・画像を抽出できた |

この測定では、対象投稿の表示と抽出は正常に動作しました。

### 原因

[scraper/auto_detect.py](../scraper/auto_detect.py) の `check_new_art_post()` は、`main` の表示とフォロワー数の取得が終わると、投稿カードの件数を直ちに数えていました。プロフィールの外枠は投稿一覧より先に表示されるため、読み込み途中の0件を「新着なし」と判定していました。

この判定後は最終チェック時刻も更新されるため、対象投稿の確認は次の新着チェックまで持ち越されていました。

### 対策

投稿カード、または「投稿なし」を示す `emptyState` が表示されるまで待ってから、新着を判定するように変更しました。

- 待機には `config.PROFILE_LOAD_TIMEOUT_SEC` と `config.PROFILE_LOAD_RETRY_TIMEOUT_SEC` を使用し、読み込み失敗時は1回だけ再試行します。
- 再試行後も失敗した場合は、読み込み失敗をログに記録します。
- 投稿一覧の読み込みに失敗した場合も、取得済みのフォロワー数を呼び出し元へ返します。

[tests/test_auto_detect.py](../tests/test_auto_detect.py) に、投稿の遅延表示、再試行後の成功、投稿なし、読み込み失敗時のフォロワー数保持を確認する回帰テストを追加しました。修正はローカルのコミット `f751df5` に記録されています。

## 2. 既存投稿のメトリクス取得が毎回タイムアウトする問題

### 事象と確認結果

対象は [投稿 `2106217722229207200`](https://x.com/nnkinnb/status/2106217722229207200) です。本番の `cron.log` では、この投稿が `2h` ステージのまま、5分おきに取得対象となっていました。各実行で30秒の応答待ちと、再試行後の45秒の応答待ちを経て、タイムアウトしていました。

本番セッションで対象URLを開くと、Xは「このポストは存在しません」と表示しました。`TweetResultByRestId` の応答はHTTP 200でしたが、本文は次のように空の投稿結果を返していました。

```json
{"data": {"tweetResult": {}}}
```

`TweetDetail` でも、`tweet-2106217722229207200` の `tweet_results` が空でした。一方、同じセッションで正常な投稿の数値は取得できました。投稿が存在しないと表示される理由が、削除によるものかどうかまでは確認していません。

### 原因

[scraper/metrics.py](../scraper/metrics.py) の `fetch_metrics()` は、数値を含む投稿結果を取得できた場合だけ待機を終了していました。空の投稿結果を取得不能の応答として扱っていなかったため、応答が返っていてもタイムアウトまで待ち続けていました。

また、[main.py](../main.py) はタイムアウト時にその作品の処理を終了するだけで、次回予定を更新していませんでした。そのため、同じ投稿が次のcron実行でも取得対象となり、待機と再試行を繰り返していました。

### 対策

空の投稿結果や明示的な閲覧不能の応答を検出した場合は、`PostUnavailableError` を返して待機を終了するように変更しました。呼び出し元ではこの例外を受け取り、現在のステージを保ったまま次回確認を24時間後へ延期します。間隔は [config.py](../config.py) の `UNAVAILABLE_POST_RETRY_SEC` で設定します。

- 次回予定はNotionとSQLiteへそれぞれ保存し、片方の保存が失敗しても、もう片方への保存を試みます。
- 取得不能の際はスナップショットを追加せず、過去の数値と現在のステージを保持します。投稿を取得できるようになれば、同じステージから収集を再開します。
- HTTP 429、GraphQLエラー、未知の応答形式は、空の投稿結果による閲覧不能と区別します。これらは応答待ちのタイムアウトを経て、既存の設定で1回再試行します。

## 3. 同じ取得処理で見つかった数値の混入への対策

回帰テストで、`TweetDetail` に含まれる最初の投稿を選ぶと、対象投稿より先に並んだ返信の数値を採用してしまうことも確認しました。取得対象の投稿IDを照合し、スレッド内の別の投稿や、別の投稿に対する応答を除外するように修正しました。`TweetWithVisibilityResults` で包まれた対象投稿も抽出できます。

また、応答ハンドラが使用する待機先を、各試行に対応する `Future` に固定しました。これにより、タイムアウトした試行の応答解析が遅れて完了しても、次の試行の結果として採用しません。

## 4. 検証結果

| 検証 | 結果 |
| --- | --- |
| メトリクス取得・収集処理のテスト | `tests/test_metrics.py` と `tests/test_collector_metrics.py` の19件が成功 |
| 全体のpytest | 96件成功、71件スキップ、非推奨警告3件 |
| 本番セッションでの修正版の実行 | 取得不能の投稿は約7.46秒で `PostUnavailableError` を返し、ページ遷移は1回で終了 |
| 同じセッションでの正常な投稿の取得 | 約9.18秒で数値を取得し、ページ遷移は1回で終了 |

実行したテストコマンド

```bash
PYTHONPATH=. .venv/bin/python -m pytest tests/test_metrics.py tests/test_collector_metrics.py -q
PYTHONPATH=. .venv/bin/python -m pytest -q
```

[tests/test_metrics.py](../tests/test_metrics.py) では、取得不能の判定、対象投稿の選択、通常の再試行、遅れて届いた応答の扱いと、応答ハンドラの解除を検証しました。[tests/test_collector_metrics.py](../tests/test_collector_metrics.py) では、一時DBを使い、履歴とステージの保持、次回予定の保存、片方の保存先が失敗した場合の動作、取得再開を確認しました。自動テストの外部サービス呼び出しはモックを使用しています。

本番でのブラウザ診断は収集処理と共通の `.process.lock` を取得してから実行しました。メトリクスの修正版はメモリ上に読み込み、診断スクリプトから本番DB・Notionへの書き込みは行っていません。
